# 评估结论（2026-07-27）

“三层能力大纲 + 第三级学习单元—原子知识点关联”应放在：

> **S3 能力—概念图建模内部，位于目标能力反推之后、先修边建模之前。**

不新增第八阶段，也不新增 `learning-architecture-builder`。当前七阶段语义契约已经把“结构是什么”归属给
`build-capability-concept-graph`；把大纲拆成独立阶段会同时产生两个结构真值源，并使 G3 无法独立判断
层级、节点、先修、评估和追溯是否一致。

S3 内部执行顺序调整为：

```text
S1 目标契约 + S2 领域证据
→ 反推目标能力与子能力
→ 组织三层能力大纲
→ 拆解原子知识点
→ 建立学习单元—知识点多对多关联
→ 建立独立的 hard / soft 先修图
→ 绑定误概念、评估、掌握与补救
→ G3 统一验收
```

四类结构必须分开：

```text
三层大纲：回答“这个领域由哪些学习单元组成”
知识点列表：回答“每个学习单元具体要掌握什么”
知识图谱：回答“这些知识点之间有什么先修和依赖关系”
学习路径：回答“这个学习者现在应该按什么顺序学习哪些节点”
```

前三者由 S3 作为一个原子工件统一生成和验收；第四个由 S5 基于 S3 图谱与 S4 学习者前沿生成。

# 一、它具体放在哪一层

完整流程继续保持七阶段：

| 阶段 | 解决的问题 | 主要产物 |
|---|---|---|
| S1 目标与成功契约 | 最终要解决什么问题 | `goal_success_contract` |
| S2 领域取证与认知全景 | 依据是什么、边界是什么 | `domain_evidence_landscape` |
| **S3 能力—概念图建模** | 稳定能力结构、学习单元、知识点和先修如何统一 | `capability_concept_graph` |
| S4 学习者诊断 | 哪些已掌握，最近学习前沿在哪里 | `learner_snapshot` |
| S5 路径与会话规划 | 当前最小可行路径是什么 | `learning_and_session_plan` |
| S6 教学交互 | 如何讲、练、问并渐隐支架 | `session_package_and_trace` |
| S7 掌握验证与重规划 | 是否掌握、更新什么、下一步去哪里 | `mastery_verification_and_replan` |

大纲—知识点关联在 S3 中的内部位置是：

```text
目标能力 / 子能力
        ↓ 组成关系
可教学、可测评的学习单元
        ↓ 多对多覆盖关系
原子知识点
        ↓ hard / soft 先修关系
能力—概念图
```

## 为什么不能直接放在学习路径规划阶段

因为三层大纲描述的是**领域本身的稳定结构**；学习路径描述的是**某个具体学习者在某个时间点所选择的子集和顺序**。

例如：

```text
完整大纲有 30 个三级学习单元
```

但某位学习者可能已经掌握其中 18 个，最终路径只需要学习 8 个，另外 4 个暂时不属于目标范围。

所以：

```text
三层大纲 ≠ 个性化学习路径
```

S5 可以按学习者状态重排、跳过或补救节点，但不能改写 S3 的知识点定义、层级归属或先修事实。若规划时发现
大纲覆盖、节点粒度或关联错误，应 `return_upstream → S3`。

## 为什么不单独增加一个阶段

- 大纲层级和知识点关联不是独立于图谱的第二份结构，而是图谱的可读组织视图。
- G3 需要同时验证目标覆盖、节点粒度、层级关联、先修边、评估与来源；拆开会造成跨门原子性缺口。
- 窄目标不一定自然形成严格的三层树；强制创建独立阶段容易为凑层级制造空节点。
- 当前七阶段契约明确要求恰好七个 repo-local stage skills；新增阶段会破坏既有 S1–S7 路由和 21 个评测基线。

外部标准也支持这种同阶段、分关系建模：1EdTech CASE 将可机读的层级框架、带唯一标识的能力条目和
条目间关联放在同一框架中，并明确支持一对多、多对多关系；`isChildOf` 与 `precedes` 是不同关联类型，
不能把目录顺序当成先修顺序。IHMC 概念图方法同样要求图围绕焦点问题，并用具名连接词形成可解释命题。

# 一-A、当前文档必须补充的逻辑

## 1. 明确一个真值源

`capability_concept_graph` 是 S3 的唯一机器可执行真值源。三层大纲是该工件中的层级视图，不再另建
`learning_architecture.json` 与图谱并行维护。人类可读大纲可以导出，但不能脱离图谱单独通过 G3。

## 2. 层级与先修必须分离

- `target_capability → sub_capability → learning_unit` 只表达组成或归属。
- `node → node` 的 `hard | soft` 边只表达学习先修。
- `display_order` 即使存在，也只用于展示；不得据此推断先修。

## 3. 学习单元—知识点必须是多对多关联

一个学习单元可覆盖多个知识点；同一跨切知识点也可被多个学习单元复用。不得复制知识点制造多个
同义 `node_id`。每条关联至少记录：

```yaml
unit_id: unit-session-recovery
node_id: n-idempotent-recovery
coverage_role: core       # core | supporting | extension
rationale: 该单元的退出能力需要学习者能设计幂等恢复
```

`coverage_role` 表达稳定的结构覆盖，不使用 `introduce/reinforce/review` 这类依赖个性化教学顺序的字段；
后者属于 S5/S6。

## 4. 稳定标识、版本和变更语义

- 学习单元、知识点和关联均使用稳定 ID，标题或措辞的小改不换 ID。
- 语义实质变化时创建新 ID，并记录替代关系或变更说明；不得让旧诊断证据静默挂到新语义。
- 任一层级、关联或先修变化都产生新的 S3 工件版本，并使依赖旧版本的 S4–S7 工件进入
  `version_conflict` 或重新计算范围。

## 5. 来源和目标双向追溯

每个学习单元必须能追溯到 S1 目标能力和 S2 来源；每个核心知识点必须能回答：

```text
它支撑哪个学习单元和目标能力？
它的领域事实依据是什么？
用哪个评估项观察？
删除或改变它会影响哪些下游工件？
```

## 6. 覆盖、孤儿和重复检查

G3 至少增加以下不变量：

- 每个 `learning_unit` 至少关联一个 `core` 知识点；
- 每个目标必需知识点至少被一个学习单元覆盖；
- 不存在指向未知 `unit_id` / `node_id` 的悬空关联；
- 不存在语义重复但 ID 不同的核心知识点；
- 每个三级学习单元均有可观察退出能力、目标追溯和来源追溯；
- 层级无环，硬先修子图无环，但两类无环检查分别执行。

## 7. 三层是语义模板，不是凑数约束

标准语义为“能力领域 → 子能力/问题族 → 可测评学习单元”。领域足够宽时使用完整三层；目标很窄时允许
学习单元直接挂到目标能力，但必须显式记录省略层级的理由。`3—7`、`2—6` 等数量只能作为人工审查提示，
不能作为无证据的硬门槛。

## 8. 失败归因和确定性路由

| 缺陷 | 主归因 | 路由 |
|---|---|---|
| 目标或范围本身冲突 | S1 | `return_upstream → S1` |
| 学习单元或节点事实无来源 | S2 | `return_upstream → S2` |
| 层级、粒度、关联、覆盖、重复或先修结构错误 | S3 | `revise_here → S3` |
| S5 发现 S3 版本/结构不可靠 | S3 | `return_upstream → S3` |

## 9. 确认策略

S3 继续使用条件确认。应向用户展示能力主干、学习单元粒度、核心关联和关键先修；只有多个可比结构会
实质改变诊断题或路径时才升级为强制确认，不要求用户逐条确认全部映射。

## 10. 与 S4–S7 的边界

- S4 在知识点节点上记录学习者证据与状态，不改层级或节点定义。
- S5 选择并排序最小连通子图，可引用学习单元作可读分组，但不把大纲顺序当路径。
- S6 记录知识点在本次会话中的讲解、练习和评估角色。
- S7 更新掌握状态并决定返工路由；结构缺陷回 S3，不能靠学习者状态修补。

# 二、三层大纲的标准定义

建议固定为下面四层结构。

```text
一级：能力领域 / 大阶段
  二级：子能力 / 问题族
    三级：可教学、可测评的学习单元
      知识点：原子概念、技能、判断方法和常见误区
```

虽然表现上存在知识点这一层，但建议称为：

> **三层大纲 + 原子知识点**

而不是“四层大纲”。

这是因为知识点后续会成为知识图谱中的原子节点，不只是目录项。

---

## 第一层：能力领域

第一层回答：

> 为了达成最终目标，需要建立哪几个大的能力系统？

例如学习 Agent Runtime：

```text
1. Runtime 基础模型
2. 工作流编排
3. 多 Agent 调度
4. 生产化与评估
```

一级节点应当是**能力领域**，不能只是资料章节。

错误示例：

```text
第一章：基本介绍
第二章：高级内容
第三章：案例
```

这只是内容排列，不是能力架构。

正确示例：

```text
1. 理解 Runtime 的执行与状态模型
2. 设计可控制的 Agent 工作流
3. 实现多 Agent 的任务调度
4. 建立可观测、可恢复的生产系统
```

---

## 第二层：子能力或问题族

第二层回答：

> 在这个能力领域内，需要解决哪几类问题？

例如：

```text
1. Runtime 基础模型
  1.1 执行生命周期
  1.2 会话与上下文
  1.3 工具与权限
  1.4 工作区与状态隔离
```

第二层最好用“可以处理的问题族”来表达，而不是单一术语。

---

## 第三层：可教学和可测评的学习单元

第三层回答：

> 哪个主题可以在一次或少数几次学习会话中完成，并独立验证？

例如：

```text
1.2 会话与上下文
  1.2.1 Session、Run、Turn 的区别
  1.2.2 上下文装载与压缩
  1.2.3 跨任务状态保存
  1.2.4 会话恢复与分支
```

每个三级单元必须能够定义：

```text
学习前需要什么
学完后能解决什么
用什么问题验证
失败后回退到哪个知识点
```

---

## 知识点：最小可诊断单元

每个三级学习单元下面，再拆成原子知识点。

例如：

```text
1.2.1 Session、Run、Turn 的区别

知识点：
- KP-001：Turn 是一次输入到输出的交互单元
- KP-002：Run 是一次完整任务执行
- KP-003：Session 保存多次 Run 之间的关联状态
- KP-004：进程生命周期不等于 Session 生命周期
- KP-005：Session 恢复需要持久化上下文、工具状态和任务状态
```

知识点应当是能够被单独判断“掌握/未掌握”的节点。

# 三、三层大纲生成规则

## 规则 1：从最终能力逆向拆解，而不是从资料目录正向抄写

首先定义最终问题：

```text
学习者最终需要解决什么真实问题？
```

然后倒推：

```text
解决目标问题
需要哪些决策能力
每项决策依赖哪些子能力
每项子能力依赖哪些概念和技能
```

这是 UbD 逆向设计思想在学习路径中的应用：先确定目标结果和掌握证据，再设计内容与活动。你上传的教学方法研究也将 UbD 描述为“期望结果 → 评估证据 → 学习活动”的逆向设计。

---

## 规则 2：每层使用不同的拆分维度

不能在同一层混用“阶段、概念、工具、活动”。

例如下面是错误结构：

```text
1. Agent Runtime
  1.1 Codex SDK
  1.2 学习基础概念
  1.3 做一个项目
  1.4 多 Agent 调度
```

这里同时出现：

* 工具；
* 学习活动；
* 概念领域；
* 能力。

正确结构应统一为能力：

```text
1. Runtime 执行模型
  1.1 执行生命周期管理
  1.2 会话状态管理
  1.3 工具调用控制
```

Codex SDK、Claude Agent SDK 只是这些能力的实现材料，不应该天然成为一级或二级分类。

---

## 规则 3：父子关系只表示“组成关系”

大纲中的父子关系表示：

```text
A 包含 B
B 是 A 的组成部分
```

不表示：

```text
A 一定先于 B 学习
```

学习顺序必须由知识图谱中的先修边决定。

例如：

```text
三级单元：
- 多 Agent 调度
- 并发控制
- 任务恢复
```

目录可能把“多 Agent 调度”放在前面，但真实先修关系可能是：

```text
并发控制
→ 任务状态模型
→ 任务恢复
→ 多 Agent 调度
```

`cn-k12-map` 也将知识点层级与先修依赖分别表达，并区分 hard 和 soft 两种先修关系。

---

## 规则 4：一级节点数量控制在 3—7 个

建议范围：

| 层级         | 建议子节点数 |
| ---------- | -----: |
| 一级能力领域     |    3—7 |
| 每个一级下的二级能力 |    2—6 |
| 每个二级下的三级单元 |    2—7 |
| 每个三级下的知识点  |   3—10 |

这不是强制数学规则，而是可维护性约束。

如果一级节点超过 8—10 个，通常说明：

* 拆分维度不统一；
* 领域边界过大；
* 某些一级节点应合并；
* 需要把目标拆成不同学习项目。

---

## 规则 5：三级节点必须能够独立验收

一个合格的三级节点至少要具备以下字段：

```yaml
unit_id: runtime-session-model
name: Session、Run、Turn 的状态边界

entry_requirements:
  - 理解进程和函数调用的基本概念

capability:
  - 能解释 Session、Run、Turn 的区别
  - 能为一个 Agent Runtime 设计状态边界

assessment:
  - 给出三个状态保存场景，让学习者判断应保存在哪一层
  - 要求学习者设计一次中断后恢复流程

exit_evidence:
  - 能独立正确分类至少 4/5 个场景
  - 能画出状态生命周期
  - 提示等级不超过 1
```

如果一个三级节点无法独立验收，通常意味着：

* 它太抽象；
* 它太大；
* 它只是标题，不是学习单元。

---

## 规则 6：知识点必须原子化

一个知识点只表达一个核心判断。

错误：

```text
理解 Session、上下文管理、记忆和恢复机制
```

这里包含了至少四件事。

正确拆分：

```text
KP-001：Session 的定义和边界
KP-002：Session 与进程生命周期的区别
KP-003：上下文窗口与持久化状态的区别
KP-004：短期状态和长期记忆的区别
KP-005：会话恢复需要保存哪些状态
```

原子知识点应满足：

```text
可以设计一道题验证
可以记录一种误解
可以标记一个掌握状态
可以单独安排一次补救
```

---

## 规则 7：每个知识点必须对应一种能力证据

不能只有“知道、了解、熟悉”。

需要使用可观察动词：

| 模糊描述       | 可验证描述               |
| ---------- | ------------------- |
| 了解 Session | 能区分 Session 与 Run   |
| 熟悉工具权限     | 能配置并解释最小权限策略        |
| 掌握任务恢复     | 能设计中断后的幂等恢复流程       |
| 理解多 Agent  | 能判断任务是否值得拆给多个 Agent |
| 熟悉评估       | 能定义成功率、成本、时延和稳定性指标  |

布鲁姆分类法可以用于标注认知深度，但不能代替能力证据。一个知识点可以分别设计解释、应用、分析和创造层级的证据。

---

## 规则 8：每个三级节点都要映射最终目标

增加字段：

```yaml
goal_trace:
  - GOAL-01
  - CAPABILITY-03
```

系统必须能够回答：

```text
为什么需要学习这个单元？
它支持最终目标中的哪项能力？
删除这个单元会影响哪个目标问题？
```

无法映射目标的内容，应当：

* 删除；
* 放入拓展阅读；
* 标记为可选节点。

---

## 规则 9：大纲保持相对稳定，路径可以动态变化

大纲描述领域结构，通常不会因为一次答题就重写。

动态变化的是：

```text
知识点掌握状态
当前学习前沿
推荐路径
教学策略
复习时间
```

例如：

```text
三层大纲不变：
1. Runtime 基础
2. 工作流编排
3. 多 Agent
4. 生产化

学习路径变化：
原路径：Session → 工具调用 → 编排 → 多 Agent
修正后：Session → 状态机 → 幂等恢复 → 编排
```

因为诊断发现学习者真正缺少的是状态机和任务恢复，而不是工具调用。

# 四、完整示例：学习 Agent Runtime 编排

## 最终目标

```text
能够基于 Codex、Claude Code 或 PI，
设计并实现一个包含 Plan → Research → Action → Check
的可恢复 Agent Runtime。
```

---

## 第一层：能力领域

```text
1. Agent Runtime 基础模型
2. Agent 工作流编排
3. 多 Agent 调度与协作
4. Runtime 生产化与评估
```

---

## 三层大纲与知识点

### 1. Agent Runtime 基础模型

#### 1.1 执行生命周期

##### 1.1.1 Agent、Runtime 与 Workflow 的边界

知识点：

* KP-001：Agent 是执行目标的行为主体。
* KP-002：Runtime 提供执行、状态、工具和生命周期环境。
* KP-003：Workflow 定义任务阶段、转移条件和控制逻辑。
* KP-004：模型调用不等于 Agent 执行。
* KP-005：Agent SDK 与模型 SDK 的职责差异。

掌握证据：

##### 1.1.2 Run、Turn、Session 和 Task 的关系

知识点：

* KP-006：Turn 是一次交互。
* KP-007：Run 是一次执行过程。
* KP-008：Task 是待完成的工作单元。
* KP-009：Session 表示一组关联执行的上下文。

# 五、S3 内部如何把大纲关联转成知识图谱

三层能力视图和学习单元—知识点关联完成后，S3 还要独立生成先修关系，并由同一个 G3 原子验收。
目录父子关系和展示顺序不得自动转换为先修边。

例如：

```text
KP-006 Session 定义
    ↓
KP-010 Session 生命周期
    ↓
上下文与持久化状态
    ↓
Checkpoint
    ↓
中断恢复
    ↓
多 Agent 任务恢复
```

对应 JSON：

```json
{
  "topicId": "runtime-recovery",
  "prerequisiteId": "session-persistence",
  "strength": "hard",
  "reason": "如果不能区分会话状态和进程状态，就无法设计进程退出后的任务恢复。"
}
```

同时也可以存在软依赖：

```json
{
  "topicId": "multi-agent-scheduling",
  "prerequisiteId": "observability",
  "strength": "soft",
  "reason": "没有可观测性也可以实现调度，但难以判断节点选择和失败原因。"
}
```

# 六、一次诊断后，路径如何变化

假设学习者的诊断结果是：

| 单元                        | 状态        |
| ------------------------- | --------- |
| Agent、Runtime、Workflow 边界 | 已掌握       |
| Run、Turn、Session          | 部分掌握      |
| 工具调用                      | 已掌握       |
| 状态机                       | 未掌握       |
| Checkpoint                | 未掌握       |
| 多 Agent 调度                | 概念了解但无法设计 |
| 可观测性                      | 已掌握基础     |

初始路径可能是：

```text
Runtime 基础
→ 工作流编排
→ 多 Agent
→ 生产化
```

诊断后应收缩成：

```text
Session 状态边界
→ 状态机
→ Checkpoint
→ 幂等恢复
→ Plan/Action/Check 状态转移
→ 多 Agent 任务交接
```

已经掌握的内容不重复讲，只安排快速验证。

# 七、每轮对话后的路径修正规则

建议知识点状态至少包含：

```text
unknown              未诊断
exposed              接触过
learning             学习中
misconception        存在误概念
provisional_mastery  初步掌握
stable_mastery       稳定掌握
decayed              可能遗忘
```

## 修正规则

### 规则 A：答错且无法解释

```text
当前知识点失败
→ 检查直接先修知识点
→ 找到最早未掌握节点
→ 插入补救学习
```

### 规则 B：答对但依赖大量提示

```text
不标记稳定掌握
→ 标记 provisional_mastery
→ 安排低提示复测
```

### 规则 C：高置信度答错

```text
标记 misconception
→ 不立即继续上层内容
→ 生成反例、对比和冲突任务
```

### 规则 D：连续两次低提示通过

```text
升级 stable_mastery
→ 跳过同层基础练习
→ 进入迁移题或下一个节点
```

### 规则 E：基础题通过但迁移题失败

```text
概念记忆已形成
但能力未迁移
→ 增加变式、真实问题和比较任务
→ 不回退到单纯重复讲解
```

### 规则 F：父级问题已经可以独立解决

```text
即便部分非关键知识点未逐一学习
也可将其移入可选路径
```

最终目标是解决问题，不是机械完成全部目录。

# 九、最终定位

整个系统中，“三层大纲 + 知识点”承担的是一个中间层：

```text
上接：目标能力和领域边界
下接：知识图谱、诊断题、教学内容和学习路径
```

它不是独立的第八阶段、最终课程目录或固定学习顺序，而是：

> **领域知识与能力的标准结构模型。**

推荐最终采用以下命名：

```text
三层能力大纲
Level 1：能力领域
Level 2：子能力 / 问题族
Level 3：可测评学习单元
Knowledge Point：原子知识与技能节点
```

这样既能用于成人技术领域，也能用于 K12 学科，不会被“章节—课时—知识点”这种传统教材结构限制。

在七阶段系统中的最终所有权为：

```text
S3：定义稳定结构、学习单元—知识点关联和先修事实
S4：叠加学习者证据与状态
S5：选择并排序个性化路径
S6：执行教学交互
S7：验证掌握并路由重规划
```
