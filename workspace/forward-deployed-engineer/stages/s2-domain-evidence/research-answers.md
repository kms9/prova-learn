## `ANS-001`：FDE 的当前共同核心与组织差异

**原始问题**：当前一手岗位描述对 FDE 的共同职责、技术深度、客户工作、生产责任和产品回流有哪些共识与差异？

**回答**：跨 OpenAI、Palantir 和当前相关职位族，稳定交集不是“驻场”这个地点标签，而是五种可观察责任：直接与客户和领域人员发现问题；把模糊需求收敛为技术范围；设计并构建真实系统；把系统推到生产并对采用或工作流影响负责；把重复模式和失败信号回流产品、模型或平台。该角色需要工程深度，也需要在技术、业务、风险和组织边界之间翻译。

差异主要来自组织切分：部分公司把业务发现交给 Deployment Strategist，把技术治理交给 Technical Deployment Lead 或 Architect；旅行比例、行业知识、合规责任、售前参与和代码所有权也随公司与项目变化。因此不能只按职位名称判定能力，必须看实际产物、决策权和生产责任。

- 支持：`SRC-101`–`SRC-104`；`EVID-201`–`EVID-205`。
- 分歧：不同公司对商业拓展、架构、交付和客户关系的拆分不一致。
- 边界：三家当前雇主与一名具名从业者样本不能代表所有地区、行业或同名岗位。
- S3 输入：角色判定节点应覆盖 discovery、scoping、build、rollout、adoption、field-to-product feedback。

## `ANS-002`：与相邻角色的可观察边界

**原始问题**：FDE 与售前、解决方案架构、咨询、客户成功、驻场外包和平台工程的可观察边界是什么？

**回答**：边界应按“谁产出什么、谁有决策权、谁对生产结果负责”判断，而不是按头衔判断。

| 相邻模式 | 通常主责 | 与 FDE 的判别点 |
|---|---|---|
| 售前 / solution engineering | 赢得机会、演示、技术可行性 | FDE 通常继续承担生产构建、上线和运行反馈 |
| solution architect | 方案与架构决策 | FDE 往往同时写生产代码并参与部署闭环；混合岗位例外 |
| 咨询 | 诊断、建议、运营或变革方案 | FDE 的核心证据包含可运行系统和技术所有权，而非只交建议 |
| customer success | 关系、采用、续约协调 | FDE 可共同负责采用，但主要证据仍含工程实现与故障闭环 |
| 驻场外包 | 按客户需求持续定制或补充人力 | FDE 必须把重复需求沉淀为可复用产品能力，并使单客户定制强度下降 |
| 平台工程 | 服务多个团队的共用底座 | FDE 从具体客户问题出发；成熟模式应把共性回流平台，而非永久分叉 |

- 支持：`SRC-101`–`SRC-104`,`SRC-110`；`EVID-201`,`EVID-202`,`EVID-204`,`EVID-212`。
- 分歧：现实岗位可以是混合体，不能把表格当作硬组织法。
- 边界：若没有生产工件、运行责任或复用回流，只凭“靠近客户”不足以称为 FDE 模式。
- S3 输入：建立 role-boundary matrix 与“产物—责任—回流”判定任务。

## `ANS-003`：问题选择与最小可行部署

**原始问题**：怎样从现场工作中选择值得部署的问题，并用 MVD、基线、评估和停止条件验证价值？

**回答**：先观察一条具体工作流，明确使用者、当前基线、决策权、失败成本和业务结果，再选择一个价值较高、范围窄、可逆且能在真实约束下验证的切片。MVD 不是功能少的 demo，而是包含真实数据或代表性样本、上下文 eval、权限和人工覆盖、上线/回滚条件、采用信号与业务指标的最小闭环。

推荐判断顺序：

1. 写出任务、用户、当前流程和可量化基线；
2. 识别数据/系统接入、错误严重度、合规和责任人；
3. 定义成功、失败、停止和 go/no-go 条件；
4. 构造代表常见分布和低频高严重度风险的评估集；
5. 小范围受控上线，采集技术质量、采用和业务结果；
6. 根据证据继续、收缩、回滚或产品化。

- 支持：`SRC-101`,`SRC-102`,`SRC-105`–`SRC-109`,`SRC-113`,`SRC-115`；`EVID-205`–`EVID-210`,`EVID-214`。
- 分歧：课程的 2–6 周可作练习规划启发，不是跨行业标准周期。
- 边界：一次离线准确率或一次成功演示不能证明部署价值。
- S3 输入：problem/value brief、baseline、MVD、contextual eval、go/no-go、rollback 节点。

## `ANS-004`：从原型到采用、扩展和产品化

**原始问题**：企业 AI 部署从原型到采用、续约、扩展和产品化的关键机制与失败模式是什么？

**回答**：可审查的生命周期是：发现工作流与价值假设 → 收敛范围和责任 → 构建最小闭环 → 上下文评估 → 受控上线 → 采用、监控和事件处理 → 复盘价值与风险 → 续约/扩展决策 → 把重复模式回流产品。成功不是单一指标，而是四层同时成立：技术可靠、用户真实采用、业务结果改善、定制经验可复用。

主要失败模式是：原型未进入真实工作流；离线评估与部署分布脱节；缺少权限、人工覆盖和升级规则；没有基线或业务 owner；用户不信任或流程未改变；生产反馈没有进入 eval；客户定制持续分叉；效果主张只依赖供应商案例或自报告。

- 支持：`SRC-101`,`SRC-105`–`SRC-109`,`SRC-113`–`SRC-116`；`EVID-203`,`EVID-205`–`EVID-211`,`EVID-215`。
- 分歧：商业续约和扩展受价格、采购与组织政治影响，不能由技术质量单独推出。
- 边界：具名厂商案例可说明机制，不能独立证明普遍 ROI。
- S3 输入：lifecycle map、technical/adoption/business/reuse 四层证据、incident/change loop。

## `ANS-005`：课程统计和案例的证据等级

**原始问题**：课程中的高影响统计和案例分别属于官方披露、独立研究、媒体转引、第三方估算还是匿名综合？哪些需要降级或保留争议？

**回答**：课程材料本身统一保持 `user_provided_unverified`，逐条主张再按来源分类。

| 课程主张类型 | 本轮处理 | 可用范围 |
|---|---|---|
| 当前 FDE 职责 | 已由 OpenAI、Palantir 当前岗位原文支持 | 可进入能力图谱，但保留组织差异 |
| NIST 治理、TEVV、监控 | 官方标准/配置文件支持 | 可作为部署控制基线，具体行业另加法规 |
| “95% 失败” | 可追到 MIT NANDA 标注 `preliminary findings` 的第三方托管副本 | 只能描述该报告的样本结论与限制，禁止改写为所有 AI 项目定律 |
| “800% 岗位增长” | 本轮未取得原始 Indeed 数据或可审计方法 | `trace_only`；不得进入能力门或市场预测 |
| 厂商客户效果数字 | 供应商发布的具名案例 | 可说明实践机制，数字不视作独立审计 |
| 匿名/综合案例 | 课程教学叙事 | 只作情境练习，不作外部事实或 ROI 证据 |

- 支持：`SRC-105`–`SRC-111`；`EVID-211`,`EVID-216`。
- 分歧：NANDA 报告的官方 canonical 发布位置和后续正式版本仍待刷新。
- 边界：证据降级不否定课程的教学价值，只限制事实强度。
- S3 输入：加入 provenance classification 与 claim-audit 节点；排除 `800%` 作为能力依据。

## `ANS-006`：何时不应采用 FDE 模式

**原始问题**：什么条件下 FDE 会演化成不可扩展的定制服务、供应商锁定、治理绕过或人员倦怠？什么时候不应使用该模式？

**回答**：以下任一条件都应触发拒绝、暂停或转型评审：工作流稳定且可用标准产品/配置完成；底层产品没有可复用能力，单客户定制强度不下降；客户没有价值 owner 或决策权；数据、接入和合规条件无法满足；部署要求绕过评估、权限、人工覆盖或事件响应；商业模式无法覆盖长期工程成本；客户无法接管关键知识；团队长期依赖英雄式支持；学习无法回流产品且形成永久分叉。

FDE 适合不确定性高、价值值得验证、需要深度技术整合且能形成产品学习的阶段。稳定问题应迁移到自助配置、解决方案模板、平台能力、合作伙伴或客户团队，而不是永久保留高强度驻场。

- 支持：`SRC-104`–`SRC-106`,`SRC-109`,`SRC-110`,`SRC-113`,`SRC-115`,`SRC-116`；`EVID-205`–`EVID-207`,`EVID-212`,`EVID-214`,`EVID-215`。
- 分歧：不存在跨行业统一的“定制比例”停止阈值，阈值需结合毛利、风险和学习价值定义。
- 边界：这里给出决策条件，不把机构观点当作经验定律。
- S3 输入：stop/transition decision、governance veto、reuse trend、handoff readiness 节点。

## `ANS-007`：区分理解与可迁移能力的评估

**原始问题**：面向学习者最终产物，哪些真实任务最能区分“理解课程”与“能做 FDE 式判断”？

**回答**：使用一组互相约束的真实产物，而不是术语问答：

1. 角色边界矩阵：根据实际责任判断是否为 FDE 式工作；
2. 问题与价值简报：用户、工作流、基线、业务 owner 和停止条件；
3. MVD 设计：数据/系统边界、最小闭环、权限、回滚和 handoff；
4. 上下文评估集与风险登记：常见分布、低频高严重度、grader 和人工覆盖；
5. 激活、采用和结果仪表：区分技术、采用、业务、复用四层；
6. 产品反馈与交接包：把重复需求转成平台改进，说明何时退出驻场；
7. 口头答辩：解释取舍、证据限制和反方条件；
8. 第二场景迁移：在不同约束下重新选择问题、控制和指标。

- 支持：`SRC-101`,`SRC-102`,`SRC-105`,`SRC-108`,`SRC-112`,`SRC-114`,`SRC-115`；`EVID-208`,`EVID-209`,`EVID-213`,`EVID-214`。
- 分歧：公开招聘材料不能提供完整评分阈值，因此阈值必须在 S3/S5 结合目标合同定义。
- 边界：真实学习者答案和提示依赖只能在 S4/S6/S7 采集，S2 不代写。
- S3 输入：把八类产物映射到原子节点、先修关系和可观察测评。

## 对 S3 的统一移交

- 稳定能力域：角色与边界、问题与价值、MVD/工程、治理与评估、采用与商业结果、产品化与退出。
- 必须进入图谱的横切规则：来源分级、上下文评估、人工覆盖、go/no-go、rollback、四层成功证据、复用趋势和第二场景迁移。
- 不进入图谱的断言：`800%` 岗位增长、把 `95%` 解释为所有 AI 项目失败、供应商案例数字的独立有效性。
- 仍需学习者行为确定的内容：技术基础、商业判断起点、风险推理、提示依赖与迁移能力。
